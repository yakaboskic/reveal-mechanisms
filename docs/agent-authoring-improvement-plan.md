## Additional problems exposed by the run

The most important instruction improvement is stronger control of query scope. Targeted absence probes covered TTD Factor1, but the account and final notes extend the absence statement to both TTD factors. Factor2's top-60 list is partial. Similarly, a small nonzero loading does not establish exclusive membership in another factor, and inspecting factor labels does not prove that no translation-related factor exists. Biological classifications of gene sets require supporting definitions or evidence, not just their names.

Add an evidence-to-assertion check before synthesis: record which factor, gene/set, model, metric, filter, page/window and coverage state supports each assertion. A claim spanning two factors needs observations covering both, or narrower wording. Ratios of stored loadings remain ratios under the model's metric semantics, not biological fold changes or confidence ratios. A disclaimer later in the account cannot repair an overstated proposition.

Retain the existing eligibility distinction: empty-query and diagnostic captures can document query coverage, but are not independently eligible scientific support. Positive source ancestry somewhere in a compound claim does not establish every constituent inference. Deterministic lint checks structure and source fidelity; it does not certify biological correctness.

The current documentation also contains conflicting requirements: some pages still require CFDE ancestry for every claim, promise a separate scientific review, or say all local starts install a DAPPER checkout. Current policy encourages CFDE grounding without requiring it; the second AI review is retired; downloaded workspaces do not contain a runnable full validator. Correct these contradictions without introducing a new mandatory review or CFDE gate.

## Work package 1 — A complete, concise authoring contract (P0)

Use one versioned contract to generate both local and hosted instructions. Keep scientific rules shared and make execution steps explicit for each mode. The initial reading path should lead through one short entry point and bounded tool responses over the original evidence.

**Design decision: remove recursive evidence-file expansion from the new workflow.** Agents need a way to read selected evidence, not a pre-generated file tree representing every JSON value. This replaces the earlier proposal to reuse the hosted view builder with more compact record files.

The expansion currently happens during hosted startup in `box_remote.py`, after the frozen package is available and before the model starts. `build_evidence_files` creates small files so the agent can inspect large/minified JSON using Read/Grep. Its 12 KB per-record limit recursively splits oversized arrays into separate element files, including individual embedding coordinates. In our in-memory audit this generated **32,728 files / 14,371,384 bytes**: 30,720 numeric coordinate files, 1,610 vector navigation files and 398 other files. Almost 99% of the files came from numeric vector expansion. These were diagnostic results held in memory; they were not written into the downloaded workspace. The expansion is an access workaround and provides no additional scientific evidence or provenance.

Ship a small, explicit workspace layout:

- `input/evidence-package.json`, its manifest and original source artifacts: exact frozen evidence and hashes, with selected later captures downloaded as described in work package 3.
- `input/evidence-index.json`: selected question, attachments/anchors, capabilities, evidence status, artifact identities, exact source pointers and reader entry points.
- `input/package-sections/authoring-schema-excerpt.yaml`: generated from the locked release, covering ScientificAccount, Proposition, Claim, EvidenceItem, ClaimScore, Mechanism, GeneSet, File and KnowledgeGap, with the transitive schema definitions needed to use them correctly. The current hosted excerpt also needs its missing Mechanism/KnowledgeGap definitions added.
- Complete, validated examples for gene–GeneSet, gene–factor and GeneSet–factor assessments, a source-result/ClaimScore pattern, and a synthesis proposition. Show structural GeneSet provenance in EvidenceItems, not only names in snippets. Mark example evidence as synthetic, never eligible sources.

Provide a shared bounded-reading contract for the original artifacts. A request identifies a permitted artifact and its frozen hash, an exact JSON Pointer or text range, and bounded paging parameters. The response returns the requested content, source identity/hash, precise locators, coverage/truncation information and continuation information when needed. Bind continuation tokens to the artifact hash and selected pointer/range. Preserve exact source values, numeric tokens and duplicate-key rejection through parsing and response serialization. Reading a frozen artifact does not re-query a scientific source, create a new scientific observation or consume the agent's scientific-query budget; enforce separate inspection response/resource limits.

The online agent uses the existing bounded scientific MCP queries for discovery and a reader for exact retained seed/capture content. The local launcher exposes the equivalent reader over manifest-verified downloaded artifacts through its local stdio tools. Offline mode keeps this local reader available while disabling remote calls; update the current behavior that disables the entire Reveal MCP bridge. An artifact not downloaded locally must be reported as unavailable offline; the reader must not silently fetch it. Resolve only manifest-listed artifact IDs or verified closure entries, reject path traversal/symlink escapes and exclude credential state. Keep existing authorization for remote private artifacts.

Keep embedding vectors and detailed retrieval diagnostics in their original audit artifacts, accessible on explicit request. Exclude them from default scientific reading. Return bounded slices on demand without materializing a file for each element or response page. Preserve exact original bytes, hashes and selected-gap identity; provenance links continue to point to the underlying source artifacts.

Remove the new hosted startup's call to recursive `build_evidence_files` and update local/hosted instructions that require `input/evidence-records/` or say tools are unnecessary for package inspection. Replace the associated hosted runtime view manifest with the reader contract/version, index hash and source inventory. Version the `dispatch_view` file-input contract, prompt hashes, runtime metadata and startup checks together. Update archive allowlists/manifests for the small index and schema files. Do not raise the ZIP file limit to accommodate expansion. Existing frozen workspaces retain their original manifests; compatibility for older record-file layouts must not cause new packages to generate them.

Correct the local instructions about shell availability, DAPPER installation, fixed hosted output paths, `write_outcome`, literature tools and lint tools. Do not present copied Python modules as an installed offline validator. A complete offline validator can be a later optional, pinned dependency bundle; shipping a schema excerpt alone does not install one.

Introduce temporary IDs such as `urn:reveal:local:<work-id>:<document-id>:proposition-1`, with sibling conventions for claims, evidence and scores. These are draft references; trusted assembly still mints final IDs. Do not reject otherwise valid legacy draft IDs solely for using the older convention.

**Acceptance:** build local and hosted workspaces from the same seed within existing archive file/byte limits, with no generated recursive `evidence-records/` tree. Adding embedding coordinates must not increase the number of workspace files. A reader can retrieve an exact membership row, loading row, gap attachment, text excerpt or requested vector slice with its original hash/locator and truthful paging status. Local offline reads make zero network calls; missing local artifacts and changed bytes fail clearly; hosted/local reads of the same artifact agree. Every mandatory linked path exists, every example passes the actual locked draft validator, generated schema definitions match the release lock, and no instruction requires a tool absent from that mode. ## Work package 2 — Trusted scientific objects for progressive discovery (P0)

**Researcher priority: encourage agents to build useful, reusable relationship claims about genes, GeneSets and factors, with GeneSets structurally reachable from the evidence that uses them.** This is a central authoring objective for local and hosted agents, not an optional documentation polish item. Agents should actively investigate the relevant relationships and express supported assessments as distinct Claims and structured Propositions; they should not stop at a prose-only account summary.

Let a selected factor discovered through MCP produce its exact DAPPER Mechanism object and dependencies under the frozen generation, using the existing import/identity rules in `reference_generation.mechanism_node` and catalog assembly. Include the pinned trait metadata needed to reproduce that object. Prefer extending `get_factor` and capture materialization over adding overlapping search tools. Provide a bounded resolver only where resolving a selected set of references requires it. Carry the resolved object IDs in result metadata and evidence closure so trusted assembly can hydrate them.

Handle three identifiers separately: source factor/gene/set key, authoritative DAPPER object ID where available, and verified external biological identifier where available. Unresolved source-local gene identity remains usable within its stated import scope; it does not become a cross-dataset identity assertion. Preserve existing GeneSet objects and their dependencies.

Show both layers in the contract: Proposition entity relationships when they accurately express the assertion, and Claim → EvidenceItem → exact source observation for support. Under the pinned schema, structured propositions must supply subject, relation and object together; text-only propositions are also valid. Include optional typed ClaimScore examples for separately assessed source results with the observed metric and precision; a loading must not become a probability. Do not force multi-entity synthesis or absence assertions into an invented subject–predicate–object triple.

The shared instructions and examples must cover all three relationship families:

| Relationship | Authoring behavior | Evidence required |
| --- | --- | --- |
| Gene → GeneSet | Assess membership or another explicitly observed relationship using the exact gene identity and GeneSet ID. State which relationship is actually supported. | Captured membership/definition records or other evidence supporting the specified relationship. A named knockout target is not automatically a member of the resulting signature. |
| Gene → factor/Mechanism | Assess the gene's observed loading or supported involvement in the particular fitted mechanism, retaining model, trait and metric scope. | Exact gene–factor result rows, plus trusted factor identity; additional biological interpretation needs its own support. |
| GeneSet → factor/Mechanism | Assess the observed projection/loading or supported involvement of the identified GeneSet in the fitted mechanism. | Exact GeneSet–factor result rows and the authoritative GeneSet definition/provenance actually used, with joint and marginal metrics distinguished. |

For each relevant family, search existing Propositions and Claims before authoring a new one, inspect scope, and retain reuse receipts when reusing an assessment. Retrieve the selected GeneSet with `get_gene_set` and inspect `get_gene_set_members` when membership matters. Resolve the factor through the trusted materialization above. Do not enumerate every possible pair or manufacture all three relationship types when evidence is unavailable. A gene and GeneSet loading on the same factor does not establish that the gene belongs to the set.

Use schema-supported provenance paths rather than adding an invented `gene_sets` field to EvidenceItem:

- `Claim → proposition → subject_entity / relation / object_entity` identifies the scientific relationship; GeneSet and Mechanism IDs are structural references.
- `Claim → has_evidence → EvidenceItem → was_derived_from` includes the exact captured File and, when its definition, membership or construction record actually informed the evidence, the exact trusted GeneSet. `was_derived_from` is multivalued and the pinned profile permits GeneSet targets. Retain both links; a GeneSet ID alone does not replace the query observation and its locator.
- `EvidenceItem → target_proposition → subject_entity / object_entity` also makes an involved GeneSet structurally discoverable without falsely asserting that an observation was derived from its definition.
- When an existing assessed relationship supports another claim, use `EvidenceItem → source_claims → Claim → structured Proposition → GeneSet/Mechanism`, preserving its original authorship and evidence dependencies.

Every GeneSet-based evidence use should therefore have an explicit, inspectable path to the exact GeneSet object and onward to its available collection/construction/source provenance. The package and export must hydrate and retain those dependencies unchanged. If upstream membership or construction provenance is unavailable, record the precise missing information; preserve known catalog provenance without claiming a complete history. Merely mentioning a GeneSet ID in prose does not meet this authoring objective. These paths are supported by the pinned schema; no DAPPER schema extension is proposed.

Add `entity-reference-missing` and a focused GeneSet-provenance finding when known selected evidence involves an available trusted entity but the authored graph retains only prose. The repair guidance should identify the actual object and missing structural path. Keep heuristic findings advisory even under strict mode, and avoid broad gene-name regexes that flag ordinary synthesis. Invalid declared references, altered trusted GeneSets and unsupported identity substitutions remain errors. The relationship templates and fixtures must explicitly demonstrate the intended complete paths even though free-form synthesis remains valid.

**Acceptance:** discover a factor absent from the seed and author a structurally linked, source-grounded account without retyping/minting trusted objects; demonstrate stable identity within a pinned import and separation across incompatible fits; reject altered dependencies and generation mismatch; verify typed metrics; retain valid narrative synthesis and independent-evidence accounts. Add positive fixtures for each of the three relationship families and a reused source Claim. Starting from each GeneSet-based EvidenceItem, programmatically reach its exact GeneSet and its available source provenance, as well as the exact result File and locator. Export/download must preserve those paths. Negative cases cover prose-only GeneSet references, an unrelated GeneSet added as a provenance shortcut, inferred membership from co-loading, and confusing a perturbation target with signature membership. Missing upstream provenance must remain explicitly incomplete rather than fabricated.

Main code: `research_data.py` (`QueryCapture.materialize`), `research_seed.py`, `acceptance.py`, `scientific_account_lint.py`, scientific reuse/dependency tests and progressive acceptance tests.
