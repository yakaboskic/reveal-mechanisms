# Files in provenance graphs

`File` is a concrete `HashableNode` for a single file used or generated by an
activity. It can represent an input, intermediate, or output without C2M2
registration or a DRS endpoint. Those roles follow from `Used` and
`WasGeneratedBy` edges. Store generic instances in the `files` document group.

`C2M2File` inherits `File` and adds `persistent_id`, `local_id`, `c2m2_uuid`,
and the `PortalLinked` mixin. Existing C2M2 field names, checksum encodings,
hashability, and identifiers are preserved. The shared fields are `name`,
`description`, `filename`, `md5` (base64), `sha256` (hex), and `size_in_bytes`.
`File` also supports `mime_type` and a `location` string, which can be a local
filesystem path, a retrieval URI, or a declared document CURIE. File metadata is optional; supply a checksum
when available to distinguish files with otherwise identical descriptions.

Use `location` for `/humgen/...` or `humgen:...` paths; declare
`humgen: file:///humgen/` in the document's `prefixes` map for the latter.
`local_id` is a source-system identifier. Native C2M2 identifies records using
`id_namespace` together with `local_id`; DAPPER's compact profile does not
model that two-column key separately. A storage path alone should not imply
C2M2 registration. The [HuBMAP example](../examples/example_geneset_hubmap.yaml)
retains C2M2 metadata only on its GMT and uses File for the other 74 records.
See [gene-set authoring](geneset-authoring.md) for collection and row references.

`DrsObject` remains separate: GA4GH DRS can describe a blob or a bundle. A file
can reference one or more blob representations through `drs_representation`
(`dapper:drsRepresentation`). The equivalent reified edge is `DrsRepresentation`,
stored under `drs_representation_edges`. A bundle that contains a file is not a
representation of that single file. DAPPER's compact DrsObject profile does not
yet model bundle contents or the full DRS API response.

`Dataset.has_file` / `HasFile` links a logical dataset to ordinary `File` or
`C2M2File` distributions. No DRS service is required. The inline `has_file`
list and `has_file_edges` graph group express the same relationship.
`Dataset.location` can record a current storage prefix; like `File.location`,
it is excluded from identity. Neither a mutable prefix nor a metadata digest
fixes the bytes in a dataset version: capture files, checksums, and an actual
manifest when available. `has_file` membership is hashable.

`Dataset.has_drs_object` / `HasDrsObject` continues to describe DRS-backed
distributions. It has different semantics from a file's optional DRS access
relationship. Registering a file with DRS does not mean an activity generated
new file bytes; it adds an access relationship to the existing provenance node.

`File.location` and `File.drs_representation` are **unhashable**. Moving a file
or registering it with a DRS service leaves its DAPPER ID unchanged. File
metadata, including checksums, is hashable. `C2M2File.local_id` retains its
existing hashable semantics as the source system's identifier. DAPPER IDs name
metadata records, not raw bytes: changing `File` into `C2M2File` changes its ID
because the class is part of the hash.

The linked file and DRS blob should agree on size and checksums for the same
bytes, with matching algorithms and normalized encodings. LinkML validates each
record's shape, not this cross-record equality. DRS uses hex checksums;
`File.md5` preserves the existing C2M2 base64 convention, so MD5 values require
encoding conversion before comparison. `File.sha256` and
`DrsObject.checksum_sha256` both use hex.

See [example_file_graph.yaml](../examples/example_file_graph.yaml): one activity
produces an intermediate file, another consumes it, and an optional DrsObject
exposes the same bytes. All values are illustrative.

The gene-set converter retains `C2M2File` for source nodes with nonempty
`c2m2_properties`. A source `File` without those properties becomes a generic
`File`; its generic fields are read directly from the node. Its `location` can
join an input metadata sidecar's `path` or `local_path` to recover SHA-256.
